Lattice quantization, from silicon to model

Siliquant rounds LLM weights onto the A16 Hamming lattice, decodes them with hand-written CUDA kernels on a laptop RTX 3080, and checks them for flipped bits at no storage cost. Four models are released with their full records.

1 · Fast on a laptop GPU
400 tok/s
CUDA kernels on an RTX 3080, end to end

Limit: one 0.5B model, batch 1, against PyTorch BF16, not against llama.cpp or Q4. The engine uses uncalibrated A16 rounding: 82% top-1 agreement with BF16 when teacher-forced, and free-running text diverges after 4 tokens.

Details

Qwen2.5-0.5B runs at 400 tokens a second on an RTX 3080 laptop GPU. That is 5.6 times faster than PyTorch BF16, and it uses 4.9 times less energy. Its linear layers are stored at 4.5 bits a weight; the embeddings and output head stay in BF16. In isolated matrix-vector kernels, pre-encoded A16 weights stream at 611 to 647 billion weights a second, at the measured memory-bandwidth ceiling. Unranking the compact hampack file on the fly reaches only 3.7 billion, so serving uses the pre-encoded layout. The method and audit program come from Foundation-0's cave-expedition and aletheia; the CUDA kernels and the decode engine were written in this repository, and neither origin repository has GPU code to compare against. Details: engine study (PR #88) and kernel study.

2 · Fewer bits, lower error than Q4_K_M
16–40% lower KL than Q4_K_M
A16 at 4.5 bits vs Q4_K_M at 4.8, no calibration data, three 1–2B models

Limit: three 1–2B models, one text. Against Q4_K_M made with an importance matrix (scored with 8-bit activations, so not exactly like-for-like), A16 is lower on Qwen2.5 (0.019 vs 0.028) but higher on SmolLM2 (0.048 vs 0.038); Llama was not tested. Not the released Hugging Face models, which use other A16 recipes and have no Q4_K_M comparison.

Details

Mean KL against the 16-bit model on WikiText-2 (10,200 positions, llama.cpp llama-perplexity): 0.019 on Qwen2.5-1.5B-Instruct, 0.048 on SmolLM2-1.7B-Instruct, 0.034 on Llama-3.2-1B-Instruct. Q4_K_M at 4.80–4.82 bits, decoded to 16 bits and scored the same way, gets 0.032, 0.072 and 0.041, so A16 is 16 to 40 percent lower. Lower error at fewer bits, with no retraining and no calibration data. These are rounded weights scored inside the 16-bit model; both sides use 16-bit activations. Stored in the packed file (18 bytes per 32 weights, read back bit for bit, ten ffn_down columns kept), A16 scores 0.021 / 0.048 / 0.027, 34 to 35 percent below Q4_K_M. Details in §04b.

3 · The format checks itself
Built-in bit-flip detection, 0 extra bytes
Bit-flip detection with no ECC hardware

Limit: the check sees only the lowest of each weight's 4 stored bits, so flips in the other 3 bits, the scales, activations or the KV cache go unseen. The Hugging Face files rely on SHA-256 checks instead. No flipped bit has been caught live in the middle of a run yet.

Details

A16 is built on the extended Hamming [16,11,4] code: in each block of 16 weights, the lowest bits of the 16 weight codes form a codeword. A single flipped low bit gives a unique fingerprint, so the check can find it; two flips in a block are detected but not located. The live engine checks every block as it decodes, on a consumer GPU with no ECC memory, at a cost of 3.1% of tokens a second on Qwen2.5-0.5B (0.4–0.7% in an isolated kernel). A kernel that also corrects the flipped bit exists but runs 26–44% slower and is not in the engine. Checked over all 65,536 possible 16-bit words. All 16 single-bit flips map to distinct fingerprints. Live full-model runs on an ASUS ZenBook with an RTX 3080 show 0 syndrome errors. Details: engine study (PR #88) and A16 kernel study.

Roofline (Bandwidth Ceiling)

TPU v5e · 819 GB/s HBM · Weight-only · Batch 1 · Exact rational

Low-batch LLM decode on TPU v5e is HBM bandwidth-bound: each generated token streams the full weight set from memory. Quantizing weights into 8-dimensional E8 lattice codes directly reduces bytes moved per token. Bandwidth ratios follow strictly from bits per weight alone: 16 / 4.50 = 3.56× and 8 / 4.50 = 1.78× (at 4.47 bpw, INT8 ratio is 1.79×). Every figure below is a theoretical memory ceiling; kernel throughput is benchmarked separately in Section 5.

Interactive HBM Bandwidth Ceiling Paper Ceiling · 819 GB/s
tok/s = (819 GB/s × 8) / (Weights × bpw)
Caveat
Gemma denominator discrepancy (unflagged in certificate source): The certificate implies 4.0B weights (yielding 102.4 FP16, 364.0 Ball, 366.4 Hadamard tok/s on v5e), whereas the scored gemma-4-E4B-it model contains approximately 7.5B weights. At 7.5B weights on TPU v5e (819 GB/s), true ceilings are approximately 55 tok/s (FP16), 182 tok/s (Q4_K_M), 194 tok/s (Ball @ 4.50 bpw), and 195 tok/s (Hadamard @ 4.47 bpw).

RTX 3080 sm86 fused A16_BlockH4 now measured at 592.31 Gw/s (0 B spill, 213.48 tok/s projected on 3B); Pallas/TPU unmeasured; Zen 1 CPU fused GEMV is 178–220× slower than Q4 proxy; the packed A16 file decodes 2.5–3.0× slower than the Z32 file on one core.
Bitrate Floor BOUNDARY INT4 raw floor sets the 4.00 bpw roofline bound. Below 4.0 bpw, KL rises sharply in measured Gemma cells; sweet spot in 4.0–5.0 bpw awaits hardware cost data.
Generalization MODEL-DEP. Zero-codeword behavior is model-dependent. Output law holds on two tested models; the third model breaks it.
Evaluation Scope SCOPE Gemma 3 270M, 1B, 4B and provisional 12B evaluated on two texts (16-bit ref), plus the Gemma 4 E4B bridge (8-bit ref). Decode baseline 18–23M w/s/core (fastest 58–65M).
